### 0.1 The red badge, explained

`PI-1` — a React `useId` hydration mismatch across the CRM shell chrome. Server
and client generate different Radix ids, so React reports an attribute mismatch
on **eight** shell controls, not one:

| control | file | attribute |
|---|---|---|
| "Add Member" ⌄ split trigger | `SplitCreateButton.tsx:185` | `id` |
| second top-bar dropdown trigger | `CrmTopBar.tsx:295` | `id` |
| Chats · Channels · Contacts · Quick Actions · Sticky Notes | `BottomBar.tsx:57/84/111/146/173` | `aria-controls` |

**Cause**, verified by experiment, not inferred: the shell interleaves five
`next/dynamic({ ssr: false })` children (`CrmShell.tsx:18-30`,
`CrmTopBar.tsx:58-68`) with those triggers, so the client hydrates a tree the
server did not render and `useId` diverges. It is intermittent because a warm
chunk cache resolves those children at a different point than a cold one — in a
two-page probe the **second** page loaded is the one that logs it, whichever
page that is. Flipping all five to SSR did not fix it; the mismatch simply moved
to the other page, so the fix is the shell's dynamic-import layout, not one
import. That is product code outside this wave's file ownership, so it is
**reported, not patched** — see the open-issues list.

**Severity is not cosmetic.** React says of this class "This won't be patched
up": the server value stays in the DOM. Five of the eight are `aria-controls`,
so assistive-tech wiring is affected, not just an internal id.

### 0.2 Verdict vs abort — why the walk still produces evidence

A diagnosed defect is still a defect, so every `PI-n` line keeps the
`page-errors` trap rows **red**, and `walk:crm:gate` exits 1. But PI-1 lives in
the *shared shell*, so it is on `/crm`, every list and every record. Two things
follow, and both were built deliberately:

* **It must not abort the run.** Throwing on it at the top of every spec aborted
  all 387 rows before the first one was measured — a red exit code and no
  evidence at all. Only an **undiagnosed** error throws
  (`hasUntrackedPageIssue`, `traps.ts`).
* **It must not be charged to task rows.** Charging it per-row turned **20 of 67**
  rows red for something none of them measures, hiding whether `NV-cross-tab` or
  `A11Y-keyboard-T1` still work. Task rows are charged only with undiagnosed
  errors; the PI-n lines still travel on the row itself as `knownIssues`, and in
  `<run>/page-errors.jsonl` whole.

The distinction is verdict vs. blast radius. The verdict is unchanged: **red**.

### 10.1 `min(uuid)` in the soft-delete RPCs — a confirmed production P0
- **File:** `supabase/migrations/20260823020000_fix_soft_delete_min_uuid.sql`
- **What is broken today, in prod:** `crm_soft_delete_records_bulk` (the only
  delete path the record page and bulk delete use) and `crm_restore_batch`
  resolve the org with `min(coalesce(organization_id, org_id))`. Postgres has
  **no `min(uuid)` aggregate**, so every call raises
  `ERROR: function min(uuid) does not exist` and `DELETE /api/crm/records/[id]`
  answers **500**. Deleting a record is broken for every tenant.
- **The fix:** `(array_agg(...))[1]` instead of `min(...)`. Both call sites
  operate under a single-org invariant (the bulk function rejects cross-org
  batches on the very next statement), so "first aggregated value" and
  "minimum" identify the same org.
- **Why it is safe:** additive and reversible — `CREATE OR REPLACE` of two
  functions, no data touched, no signature change. Rollback = re-run the two
  definitions from `202607140003_crm_records_soft_delete.sql` (the migration
  carries that block at the end).
- **What proves it:** applied on the local stack (`schema_migrations` row
  `20260823020000`; both functions verified to contain `array_agg`), and the
  behaviour is walked end-to-end by **`FB-5-delete-undo`** — ⋯ → Delete Record →
  honest confirm → `movedToTrash()` toast → Undo → `restored()`, 4/4 clicks,
  green on desktop-1440 and tablet-1024 in both admin runs.

### 10.2 `crm_field_distinct_values` RPC (DE-2 / D4 server half)
- **File:** `supabase/migrations/20260823010000_crm_field_distinct_values_rpc.sql`
- **What it does:** org-scoped "distinct values + counts" for one JSONB key of
  one module, feeding the free-text suggestions on Health Insurance Plan.
- **Why it is safe:** `SECURITY INVOKER` — the `GROUP BY` runs under the
  caller's own `crm_records` RLS, so nothing is counted that the caller could
  not already list, and an other-org module id simply returns zero rows. The
  key must match `^[a-z0-9_]{1,64}$` (never interpolated), `p_limit` clamps to
  1..200, soft-deleted rows and blanks are skipped, values come back exactly as
  stored. `EXECUTE` revoked from `PUBLIC`/`anon`, granted to `authenticated` and
  `service_role`. Additive, idempotent, rollback is a single `DROP FUNCTION`.
- **What proves it:** applied locally (`schema_migrations` row
  `20260823010000`) and exercised through the drawer by `DE-paste` /
  `DE-open` in all six runs. Prod does **not** have it.
